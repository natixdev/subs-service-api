# API для управления личными подписками и регулярными платежами

REST API для управления финансовыми обязательствами: подписки, счета, страховки и гарантии

Стек:

- Python 3.13
- FastAPI
- PostgreSQL
- SQLAlchemy 2.x (async)
- Alembic
- Docker Compose
- pytest


## Запуск приложения:

```bash
docker compose up --build
```

При старте автоматически:

* запускается PostgreSQL
* применяются миграции Alembic
* запускается FastAPI

Документация (Swagger):

```
http://localhost:8000/docs
```

## Архитектура

Структура проекта:

```
app/
├── api/            # HTTP endpoints
├── services/       # бизнес-логика
├── repositories/   # запросы к БД
├── models/         # SQLAlchemy модели
├── schemas/        # Pydantic схемы
└── core/           # настройки, БД, ошибки, SSE
```

Логика разделена по слоям:

* API отвечает за HTTP;
* service содержит бизнес-правила;
* repository работает только с БД.

## Lazy expiry

Перед выдачей списка (`GET /obligations`) выполняется проверка просроченных разовых обязательств.

Если:

```
status = active
recurrence = null
next_payment_date < today
```

то статус меняется на:

```
expired
```

Рекуррентные обязательства не переводятся в `expired`.

Причина: подписка или регулярный сервис продолжают существовать, даже если дата платежа прошла.
Например, пропущенная дата оплаты Netflix не означает, что подписка закончилась. Пользователь может оплатить её позже.

## Рекуррентные платежи

При оплате подписки новая дата рассчитывается от текущего `next_payment_date`, а не от даты оплаты.
Это предотвращает накопление смещения при просроченных платежах.

Примеры:

| Дата                       | Период    | Результат  |
| -------------------------- | --------- | ---------- |
| 31 января                  | monthly   | 28 февраля |
| 31 января (високосный год) | monthly   | 29 февраля |
| 15 марта                   | quarterly | 15 июня    |

## Дубликаты

При создании проверяется наличие активного обязательства с таким же названием без учёта регистра.
Дубликат не блокируется: запись создаётся, но клиент получает `warning`.
Это позволяет обрабатывать повторный импорт одного и того же платежа.

## SSE

После удаления обязательства отправляется событие:

```json
{
  "type": "obligation_deleted",
  "id": "uuid"
}
```

## Принятые компромиссы

### Lazy expiry

Логика выполняется перед получением списка, как требует ТЗ.
В более нагруженной системе можно вынести обработку в фоновую задачу.

### Транзакции

Изменения обязательства и создание платежа выполняются в одной транзакции PostgreSQL.
SSE отправляется только после успешного commit, поэтому клиент не получает событие об операции, которая не сохранилась.

### Инфраструктура

Redis, Celery и т.п. не добавлялись, так как для текущего тестового они усложнили бы проект без необходимости.

## Примеры запросов

Создание обязательства:

```bash
curl -X POST http://localhost:8000/obligations \
-H "Content-Type: application/json" \
-d '{
  "title": "Яндекс.Плюс",
  "amount": 299,
  "currency": "RUB",
  "category": "subscription",
  "recurrence": "monthly",
  "next_payment_date": "2026-07-20"
}'
```

Список обязательств:

```bash
curl http://localhost:8000/obligations
```

Ближайшие платежи:

```bash
curl "http://localhost:8000/obligations/upcoming?days=7"
```

Оплата:

```bash
curl -X POST http://localhost:8000/obligations/{id}/pay
```

Отмена:

```bash
curl -X PATCH http://localhost:8000/obligations/{id}/cancel
```

Удаление:

```bash
curl -X DELETE http://localhost:8000/obligations/{id}
```
